# Lab 3: M and C, RV32 vs RV64

Source for the instructions: The RISC-V Instruction Set Manual, Volume I (CC BY 4.0),
chapters "M Extension for Integer Multiplication and Division", "C Extension for Compressed
Instructions" and "RV64I Base Integer Instruction Set". Nothing is quoted from it; every
address, word and value below comes from the four lab ELF files.

You will build one small C program four ways, and see what changes: how many bytes the code
takes, the bits of each instruction, and what the same multiply gives on a 32-bit and a
64-bit hart.

The program is
[`mc.c`](https://github.com/RetroCoreLabs/riscv-course/blob/main/labs/03-mc/mc.c):

```c
long results[3];

__attribute__((noipa)) long product(long a, long b)      { return a * b; }
__attribute__((noipa)) long quotient(long a, long b)     { return a / b; }
__attribute__((noipa)) long remainder_of(long a, long b) { return a % b; }

int main(void)
{
    results[0] = product(100000, 100000);
    results[1] = quotient(-7, 2);
    results[2] = remainder_of(-7, 2);
    return 0;
}
```

`noipa` stops the compiler from working the answers out while it compiles, so each one is
really computed by the hart. The start-up file,
[`start.S`](https://github.com/RetroCoreLabs/riscv-course/blob/main/labs/03-mc/start.S),
is the one from chapter 1: set `sp`, call `main`, switch the machine off. It is built with
`-O1`, so each function is as short as it can be.

## 1. Concept

**M** adds multiply and divide: `mul`, `div`, `rem` and a few more. Without M, the compiler
calls a library routine instead. Two rules to know:

- Signed division rounds toward zero. -7 / 2 is -3, and -7 % 2 is -1.
- Dividing by zero does not trap. The quotient is all ones (-1). Try it in step 4.

**C** adds 16-bit forms of the instructions programs use most. Each 16-bit instruction
stands for exactly one 32-bit one. The hart tells them apart by the two lowest bits: `11`
means a 32-bit instruction, anything else means 16 bits. Both kinds mix freely in one
program.

Here is `c.li a1, 2`, the half-word `0x4589`. It stands for `addi a1, zero, 2`:

```text
 15  13  12  11     7 6      2 1  0
+------+----+--------+--------+----+
| 010  | 0  | 01011  | 00010  | 01 |
+------+----+--------+--------+----+
  c.li  imm[5] rd=x11  imm[4:0]  not 11:
               (a1)    = 2       16 bits
```

**RV32 and RV64** differ in register width: 32 bits or 64 bits. In C, a `long` is as wide as
a register (the ILP32 and LP64 conventions). RV64 adds `ld` and `sd` to load and store 64 bits,
and "W" forms such as `addiw` that work on the low 32 bits.

The four builds, from objdump of the ready-built files:

| | `rv32im` | `rv32imc` | `rv64im` | `rv64imc` |
|---|---|---|---|---|
| Bytes of code | 152 | 100 | 152 | 108 |
| `product` at | `0x80000024` | `0x8000001E` | `0x80000024` | `0x80000020` |
| `mul a0,a0,a1` | `02b50533` | `02b50533` | `02b50533` | `02b50533` |
| return | `00008067` `ret` | `8082` `c.jr ra` | `00008067` `ret` | `8082` `c.jr ra` |
| store result | `00a42023` `sw` | `c008` `c.sw` | `00a43023` `sd` | `e008` `c.sd` |
| call `main` | `034000ef` `jal` | `2025` `c.jal` | `034000ef` `jal` | `02a000ef` `jal` |
| `results` at | `0x80000098` | `0x80000064` | `0x80000098` | `0x80000070` |

Things to notice:

- `mul` is the same word in all four builds. It has no 16-bit form.
- The C builds are about a third smaller.
- RV64 has no `c.jal`; that bit pattern means `c.addiw` there. So the `rv64imc` call to
  `main` stays 4 bytes, and that build is 8 bytes bigger than `rv32imc`.
- The program is the same, but the results are not:

| | `results[0]` = 100000 × 100000 | `results[1]` = -7 / 2 | `results[2]` = -7 % 2 |
|---|---|---|---|
| RV32 | `0x540BE400` | `0xFFFFFFFD` (-3) | `0xFFFFFFFF` (-1) |
| RV64 | `0x2540BE400` | `0xFFFFFFFFFFFFFFFD` (-3) | `0xFFFFFFFFFFFFFFFF` (-1) |

10,000,000,000 needs 34 bits. RV64 keeps it all; RV32 keeps the low 32 bits.

## 2. Run

From the course folder, with either program, the RV32 build with C:

```text
retrocore --machine riscv32-bare --script labs/03-mc/run-rv32.txt
retrocore-cli --machine riscv32-bare --script labs/03-mc/run-rv32.txt
```

The program runs and switches the machine off. At the command line, type:

```text
mem.dump 0x80000064
```

The first twelve bytes are `00 E4 0B 54`, `FD FF FF FF` and `FF FF FF FF`: the three
results, each lowest byte first.

RetroCore has no bare RV64 machine yet. `riscv64-nuttx` has an RV64 hart on the same memory
map, and the script's `machine.load` puts the lab program in RAM and starts it instead of NuttX:

```text

retrocore-cli --machine riscv64-nuttx --script labs/03-mc/run-rv64.txt
```

There `mem.dump 0x80000070` starts `00 E4 0B 54 02 00 00 00`: the same low half, and a 2 on
top.

The builds without C, `mc-rv32im.elf` and `mc-rv64im.elf`, are in the same folder. Load one
with `machine.load` and its path at the command line; their results are at `0x80000098`.

## 3. Debug

Start the RV32 machine with `--dap`, so the machine waits for the debugger:

```text
retrocore --machine riscv32-bare --script labs/03-mc/run-rv32.txt --dap
retrocore-cli --machine riscv32-bare --script labs/03-mc/run-rv32.txt --dap
```

The steps use the debugger commands at the program's command line. A DAP client on the debugger
port sees the same session. RetroCore has no VS Code extension for RISC-V yet.

1. Stop at `product`:

   ```text
   break.set 0x8000001E
   cpu.continue
   cpu.reg a0
   cpu.reg a1
   cpu.reg ra
   ```

   You see `a0 = 0x186A0   (32-bit)` and the same for `a1`: 100000. `ra = 0x80000040` is
   where `product` returns to in `main`.

2. Look at the code and its bytes:

   ```text
   cpu.disasm --addr 0x8000001E --count 2
   mem.dump 0x8000001E
   ```

   The disassembly shows `mul a0, a0, a1` at `0x8000001E` and `c.jr zero, 0(ra)` at
   `0x80000022`. The debugger gives a 16-bit instruction its own name, `c.jr`, and the
   operands of the 32-bit instruction it stands for, `jalr zero, 0(ra)`.

   The bytes start `33 05 B5 02 82 80`: four bytes of `mul`, then two of `c.jr`.

   (screenshot: cpu.disasm and mem.dump at product)

3. Step both instructions:

   ```text
   cpu.step
   cpu.reg a0
   cpu.step
   cpu.pc
   ```

   After the first step `a0 = 0x540BE400   (32-bit)`: the low 32 bits of 10,000,000,000.
   The second step runs the 2-byte `c.jr`, and `cpu.pc` shows `PC = 0x80000040`, back in
   `main`.

4. `cpu.continue` runs the program to the end. `mem.dump 0x80000064` shows the three results.

Now the same on RV64. Start the program again with `--machine riscv64-nuttx`, the script
`run-rv64.txt` and `--dap`. In that build `product` is at `0x80000020`:

```text
break.set 0x80000020
cpu.continue
cpu.step
cpu.reg a0
```

You see `a0 = 0x2540BE400   (64-bit)`: the same instruction word, the whole answer.

This lab does not use the UART.

## 4. Try

Change one line in `mc.c`:

```c
    results[1] = quotient(-7, 0);       /* was: quotient(-7, 2) */
```

**Predict:** no trap. `results[1]` is all ones, `0xFFFFFFFF` (-1). `results[2]` still
divides by 2, so it stays -1.

In the `rv32imc` build only one instruction changes: `c.li a1, 2` at `0x8000004A` becomes
`c.li a1, 0`, the half-word `0x4581`. Check it in the debugger: start the RV32 machine with
`--dap` as in step 3, then before `cpu.continue` type:

```text
mem.write 0x8000004A 8145
cpu.continue
mem.dump 0x80000064
cpu.reg mcause
```

The bytes at `0x80000068` are `FF FF FF FF`, and `mcause = 0x0`: no trap was taken.

If you have the RISC-V GCC toolchain, rebuild the ELF files instead. Run these inside the lab
folder:

```text
riscv64-unknown-elf-gcc -march=rv32im  -mabi=ilp32 -mcmodel=medany -nostdlib -nostartfiles -static -O1 -ffreestanding -T link.ld start.S mc.c -o mc-rv32im.elf
riscv64-unknown-elf-gcc -march=rv32imc -mabi=ilp32 -mcmodel=medany -nostdlib -nostartfiles -static -O1 -ffreestanding -T link.ld start.S mc.c -o mc-rv32imc.elf
riscv64-unknown-elf-gcc -march=rv64im  -mabi=lp64  -mcmodel=medany -nostdlib -nostartfiles -static -O1 -ffreestanding -T link.ld start.S mc.c -o mc-rv64im.elf
riscv64-unknown-elf-gcc -march=rv64imc -mabi=lp64  -mcmodel=medany -nostdlib -nostartfiles -static -O1 -ffreestanding -T link.ld start.S mc.c -o mc-rv64imc.elf
```

Only `-march` and `-mabi` change. `-mcmodel=medany` lets RV64 code reach RAM at
`0x8000_0000`; the RV32 builds use it too, so the four differ in nothing else.

RetroCore's unit test `RiscVLabTests.Lab03_Try_DivideByZero_GivesAllOnes_WithoutATrap` writes the same
half-word and checks the values. `Lab03_FourBuilds_HaveTheChapterSizesAndWords`,
`Lab03_Rv32Builds_WrapTheProduct_AndRoundTheQuotientTowardZero`,
`Lab03_Rv64Builds_KeepTheWholeProduct` and `Lab03_StepProduct_OnRv32AndRv64` check every
size, word and value in this chapter.
